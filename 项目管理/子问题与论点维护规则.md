# 子问题与论点维护规则

本页落实2026-11-04讨论确认的组织模型：主题长期存在，子问题与论点独立成页，关系多于树状层级。规则以判断指引为主，不设字数、数量或自动合并阈值。

## 三个层次的职责

| 层次 | 回答什么 | 维护什么 | 不承担什么 |
|---|---|---|---|
| 主题 | 一个长期研究范围及其总体认识 | 范围、研究逻辑、子问题组织、跨问题综合 | 单个结论，或仅作链接目录 |
| 子问题 | 需要解释、比较或检验的具体问题 | 问题、边界、不同回答、分歧与缺口 | 孤立提问，或临时任务清单 |
| 论点 | 对问题的一项可独立讨论、引用和修订的回答 | 主张、依据、适用条件、状态、反例 | 脱离条件的一句话，或原文摘抄 |

主要阅读路径为“主题 → 子问题 → 论点 → 依据”，但关系允许多对多：一个问题可有多个竞争论点；一个论点可回答多个问题、被多个章节采用。**文件夹管存放，链接管关系，大纲管论证顺序。**

## 纳入与日常记录

- 正式进入研究的子问题和论点，从一开始就建立独立页面，不依赖以后拆分。
- 随手想法、临时提问、试画内容可以留在日常记录中，不要求立即建页；只有准备作为长期依据或引用时才接入。
- 不为补齐结构而给每个问题编造结论；问题可以长期没有论点页。
- 论点可以停留在候选或被反驳状态；独立成页不等于已成立。

## 命名与身份

| 对象 | 文件名 | 稳定标识 |
|---|---|---|
| 子问题 | `问题/Q-NN-短题.md`，NN按主题内创建顺序 | frontmatter `wiki_id: q-…` |
| 论点 | `论点/C-NN-短题.md`，NN按主题内创建顺序 | frontmatter `wiki_id: c-…` |
| 模板 | `项目管理/模板/子问题模板.md`、`论点模板.md` | — |

编号一经创建不再重排；问题顺序由 `order` 决定，与文件名编号无关。改名只改标题，不改已发布的 `wiki_id` 和文件名；确需改文件名时同步全部引用。

论点默认放在其主要维护主题下。跨主题复用时在 `primary_topic` 保留维护归口，在正文或关系字段说明其他用途；不复制正文。已有定义、基准、案例JSON和证据记录仍在原主源维护，论点页只作解释与链接，不成为第二份定义。

## 最小字段

子问题页：

- `wiki_id`、`type: research-question`、`status`、`question_title`、`primary_topic`
- `order`、`logic_role`（前提／比较／解释／表达／检验／综合）
- `summary`、`created`、`updated`

论点页：

- `wiki_id`、`type: research-claim`、`status`、`claim_title`、`primary_topic`
- `claim_kind`（原文结论／文献综合／研究判断／候选规则／工作规则）
- `claim_questions`（至少一个）
- `claim_evidence`（至少一项，含 `source`、`locator`、`use`）
- `summary`、`created`、`updated`

状态词表分开使用：论点用 `candidate`（候选）、`working`（工作中）、`supported`（有据支持）、`contested`（有争议）、`superseded`（已被替代）；问题用 `open`、`active`、`resolved`、`merged`、`retired`。“已采用”“已验证”“已写入正文”不进入这两套状态，分别由章节采用关系和证据状态维护。

## 关系词表

| 关系 | 含义 |
|---|---|
| `supports` | 为该论点提供支持，但不一定充分 |
| `qualifies` | 增加适用条件或限制 |
| `contradicts` | 与之冲突，需要并列保留 |
| `refines` | 细化或推进同一方向 |
| `supersedes` | 替代旧论点；旧页保留并标注 |
| `depends_on` | 论证上以其为前提 |

关系只表达已判断的知识联系，不因共词、同标签或链接数自动建立。

## 复用、迭代与新建

**核心原则：卡片数量随独立认识增长，不随资料份数、讨论次数或引用次数增长。**

判断时先看“是否还是同一个论点”，而不是标题相似度：

| 新出现的内容 | 优先处理 |
|---|---|
| 同一论点用于另一问题或章节 | 引用原卡，在使用处说明用途 |
| 新来源支持同一判断 | 补充原卡证据，保留来源定位与口径 |
| 更清楚的表述、解释或例子 | 优化原卡，保持核心含义 |
| 同一候选得到进一步检验 | 更新证据和状态，不另建“已验证版” |
| 发现限定条件或局部反例 | 先判断能否把原主张说准确 |
| 可独立成立、也可独立被反驳的新判断 | 新建论点并建立关系 |
| 真正不同的解释或对立观点 | 分别保留并建立关系，不为减少卡片而消除分歧 |

新建前先问：

1. 现有论点是否已经表达了这个意思？
2. 加进原卡后，是让它更完整，还是开始回答另一件事？
3. 新判断是否需要自己的证据、适用范围与审核状态？
4. 将来是否有必要单独引用、讨论或修订？

“可以独立成立或被反驳”是提示，不是硬性拆分标准。长而完整不等于必须拆；短而独立也不等于必须合并。

## 实质修订与替代

- **表述、证据、解释改善**：直接完善原卡，不建版本卡，不维护逐次修改日志。
- **核心回答或适用条件改变**：保留原判断及其状态，建立新论点并以 `supersedes` 或 `qualifies` 说明关系；核对受影响的问题与引用。
- **事实性错误、误引、抄录错误**：明确纠正，不把错误包装成并列的长期观点。

判断是否属于实质修订，可问：过去引用这张卡的人，看到修改后的内容，还会认为自己引用的是同一个意思吗？明显否定时，不应静默覆盖。

从“某组样本中观察到某现象”改为“普遍存在某规律”，通常不是措辞增强，而是新增了主张范围，不能直接改原卡。

## 拆分、合并与保留

- 拆分理由应是同一页中出现了可分别讨论、证据或状态不同的主要判断，而不是页长。
- 合并前必须核对主张、范围、来源身份与用途；相似、同标签、低链接数都不构成合并理由。
- 竞争解释、作者结论与我们的工作规则不是重复，不合并。
- 同一结论的多个来源汇入同一论点的证据表，来源分别保留。
- 合并须保留有价值内容、来源和原引用入口；拿不准时先标注“可能重复”，不强行合并。
- 暂未使用、已被否定或等待回答的内容可以降低展示优先级，不因年龄或引用少而删除。

## 接入检查

正式整理一个子问题或论点时，以下同时成立才算接入：

1. 页面有独立身份与最小字段；
2. 能从所属主题或问题找到它；
3. 论点至少回答一个问题，并说明与上层研究任务的关系；
4. 依据保留来源与定位，适用范围和状态明确；
5. 派生视图已同步，或明确标记待同步。

不为每次修改新建管理台账；影响较大的新建、拆分、合并或替代，在交付说明中用一句话交代理由即可。

## 视图与唯一主源

- 主题页的“子问题与研究逻辑”、问题页的“当前回答与关联论点”、论点页的“关联入口”、`项目管理/研究论证索引.md` 与 `研究论证关系.json` 均由 `项目管理/健康检查/research_claims.py` 生成。
- 生成器只读各页主源，不判断研究真假，不自动合并、拆分或升格。
- 章节目录只在 `论文章节/大纲结构.yaml` 维护采用关系；论点页不另记“已采用”状态。
