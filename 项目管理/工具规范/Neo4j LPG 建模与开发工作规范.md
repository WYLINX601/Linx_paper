# Neo4j LPG 建模与开发工作规范

**版本：2.0**

**用途：** 作为 AI Agent 设计、构建、维护及使用 Neo4j LPG（属性图）的基础知识与行为规范。

## 一、LPG 的定义与基本原理

### 1.1 什么是 LPG

LPG 全称 Labeled Property Graph，即标签属性图。

LPG 是一种图数据模型，用于将信息组织为节点、关系、标签、关系类型和属性。

它的基本思想是：

- 使用节点表示实体。
    
- 使用标签定义实体类别。
    
- 使用关系表达实体之间的联系。
    
- 使用关系类型定义联系的语义。
    
- 使用属性描述节点和关系。
    
- 通过路径表达和查询多层实体联系。
    

LPG 是数据模型，Neo4j 是图数据库，Cypher 是图查询语言。三者不应混淆。

知识图谱可以使用 LPG 实现，但 LPG 不一定具有知识图谱所需的语义规范、实体对齐和知识治理能力。

### 1.2 Node：节点

**定义：** 节点是图中具有独立身份的数据对象，用于表示业务领域中的实体、概念、事件或其他可独立识别的对象。

例如：

- Person：一个人
    
- Project：一个项目
    
- Task：一项任务
    
- Document：一份文档
    
- Agent：一个 AI Agent
    
- Concept：一个知识概念
    

节点的特征：

1. 每个节点都是一个独立的图元素。
    
2. 节点可以拥有零个或多个标签。
    
3. 节点可以拥有多个属性。
    
4. 节点可以与其他节点建立关系。
    
5. 节点允许没有任何关系，也允许建立指向自身的关系。
    

示例：

```
(:Project {
  id: "p001",
  name: "Linx",
  status: "active"
})
```

**建模原则：** 当一个对象需要独立识别、查询、更新，或需要与其他对象建立关系时，应考虑将其建模为节点。

不应仅因为某项信息存在，就将其自动转成节点。

### 1.3 Label：标签

**定义：** 标签用于对节点进行分类，表示节点属于什么类别或承担什么角色。

例如：

```
(:Project)
(:Document)
(:Agent)
```

一个节点可以有多个标签：

```
(:Agent:Researcher)
```

这表示同一个节点既属于 Agent 类别，也属于 Researcher 类别。

标签的特征：

1. 标签作用于节点，不作用于关系。
    
2. 一个节点可以拥有零个或多个标签。
    
3. 标签可以用于节点匹配、分类和索引。
    
4. 标签可以动态添加或删除。
    
5. 标签不等同于属性，也不自动规定节点必须有哪些属性。
    

**建模原则：** 优先使用标签表达稳定的实体类别或具有查询价值的分类。

状态也可以使用标签表示，但频繁变化的普通状态通常更适合属性。

### 1.4 Property：属性

**定义：** 属性是节点或关系上的键值对，用于记录数据对象或联系的具体特征。

例如：

```
(:Task {
  id: "t001",
  title: "构建知识图谱",
  status: "running",
  priority: 1
})
```

属性的特征：

1. 节点和关系都可以拥有属性。
    
2. 属性由名称和具体值构成。
    
3. 不同节点可以具有不同属性。
    
4. 属性可以用于筛选、排序、统计和索引。
    
5. 属性支持多种数据类型，例如字符串、数字、布尔值、时间和符合要求的列表。
    
6. 不可将任意嵌套 JSON 对象直接持久化为属性。
    
7. 设置属性为 `null` 通常意味着移除该属性，而非保存一个普通的 null 值。
    

**建模原则：** 当信息主要用于描述某个对象，而且不需要独立身份或建立其他关系时，优先将其建模为属性。

例如，任务优先级通常是属性，而不是独立节点。

### 1.5 Relationship：关系

**定义：** 关系是两个节点之间具有明确方向的连接，用于表达实体之间的语义联系。

例如：

```
(:Project)-[:HAS_TASK]->(:Task)
```

表示一个项目包含一项任务。

关系的特征：

1. 每条关系具有一个起始节点和一个终止节点。
    
2. 每条关系具有方向。
    
3. 每条关系必须有且只有一个关系类型。
    
4. 关系可以拥有属性。
    
5. 两个节点之间可以存在多条关系。
    
6. 一个节点可以与自身建立关系。
    
7. 查询时可以按照关系方向遍历，也可以使用不限制方向的匹配方式。
    

关系方向不代表所有业务联系天然都是单向的。它是图中的存储与查询结构，需要结合业务语义解释。

**建模原则：** 当信息表达两个可识别实体之间的联系，而且这种联系需要被查询、遍历或分析时，应优先考虑关系。

### 1.6 Relationship Type：关系类型

**定义：** 关系类型用于明确关系表达的语义，即两个实体之间究竟存在什么联系。

例如：

- `HAS_TASK`：包含任务
    
- `DEPENDS_ON`：依赖
    
- `EXECUTES`：执行
    
- `REFERENCES`：引用
    
- `BELONGS_TO`：归属
    
- `MENTIONS`：提及
    

关系类型与标签的区别：

- 标签定义节点是什么类别。
    
- 关系类型定义两个节点之间存在什么联系。
    

例如：

```
(:Agent)-[:EXECUTES]->(:Task)
```

Agent 和 Task 是节点标签，EXECUTES 是关系类型。

**建模原则：** 优先使用能够明确表达业务语义的关系类型。

避免在已有明确语义时滥用 `RELATED_TO` 等宽泛类型。

关系类型应规定允许的起点类别、终点类别、方向和业务含义。

### 1.7 Relationship Property：关系属性

**定义：** 关系属性描述的是两个节点之间某次或某种联系的特征，而不是节点自身的特征。

例如：

```
(:Agent)-[:EXECUTES {
  assignedAt: datetime("2026-10-23T10:00:00"),
  role: "primary"
}]->(:Task)
```

其中 `assignedAt` 和 `role` 描述的是这条执行关系。

判断方法：

- 描述 Agent 自身的信息，应放在 Agent 节点上。
    
- 描述 Task 自身的信息，应放在 Task 节点上。
    
- 描述 Agent 与 Task 之间的联系，应考虑关系属性。
    

如果一次执行具有独立生命周期、日志、产出、状态变迁等复杂信息，应考虑将 `Execution` 建模为独立节点，而不是无限增加 EXECUTES 关系的属性。

### 1.8 Path：路径

**定义：** 路径是图中由节点和关系交替组成的连续序列，用于表达实体之间的直接或间接连接。

例如：

```
Project → Task → Document → Concept
```

路径能够支持：

- 直接关联查询
    
- 多跳关系查询
    
- 依赖追踪
    
- 影响范围分析
    
- 最短路径搜索
    
- 知识溯源
    

示例：

```
MATCH p =
  (a:Project)-[:HAS_TASK]->(t:Task)
RETURN p
```

注意：

1. 路径通常是通过图查询得到的结果，不需要为每条路径额外创建节点。
    
2. 路径长度通常以经过的关系数量衡量。
    
3. 多跳遍历不应无限制执行。
    
4. 路径存在，只能说明节点之间存在对应连接；不代表两者具有因果关系。
    
5. 不同的路径查询模式，对节点或关系的重复访问可能有不同规则。
    

### 1.9 Schema：图模式

**定义：** 在设计层面，Schema 用于规定一个业务领域中允许出现的节点、关系和属性结构。

建议记录：

- 节点标签及含义
    
- 属性名称、类型和用途
    
- 稳定标识与唯一性规则
    
- 关系类型、方向和端点类别
    
- 必填属性
    
- 允许的取值范围
    
- 关系数量约束
    
- 时间及来源字段
    
- 数据权限与更新规则
    

需要区分：

**逻辑 Schema：** 应用层的数据模型及语义规范。

**数据库 Schema：** Neo4j 数据库中的索引、约束及版本支持的其他模式定义机制。

Neo4j 可以在没有预定义 Schema 的情况下写入数据，但不代表生产应用不需要 Schema。

应用层的所有逻辑规则，也不一定都能被数据库约束直接强制执行。

## 二、LPG 建模判断规则

AI 在设计节点、属性和关系时，必须依据数据的语义及查询需求做出选择。

### 2.1 节点、属性和关系的选择

**使用节点，当：**

- 对象具有独立身份。
    
- 对象需要被多个其他对象引用。
    
- 对象需要独立管理生命周期。
    
- 对象需要与其他实体建立多种联系。
    

**使用属性，当：**

- 信息主要描述一个节点或关系。
    
- 信息无需独立身份。
    
- 信息只需要进行筛选、排序或统计。
    
- 将其单独建模为节点不会带来有价值的查询能力。
    

**使用关系，当：**

- 两个独立实体之间存在业务联系。
    
- 联系本身具有明确语义。
    
- 需要沿该联系进行查询或分析。
    
- 需要表达引用、依赖、归属、执行等关系。
    

### 2.2 典型建模对比

场景一：项目状态

推荐：

```
(:Project {status: "active"})
```

一般不推荐：

```
(:Project)-[:HAS_STATUS]->(:Active)
```

普通状态通常不需要独立节点。

场景二：任务负责人

推荐：

```
(:Agent)-[:ASSIGNED_TO]->(:Task)
```

如果 Agent 是独立管理的实体，就不应仅将其名称保存为任务属性。

场景三：任务执行记录

简单执行关系：

```
(:Agent)-[:EXECUTES]->(:Task)
```

复杂执行过程：

```
(Agent)-[:PERFORMS]->(Execution)
(Execution)-[:OF_TASK]->(Task)
```

当执行过程需要记录独立 ID、日志、时间、结果和状态时，Execution 节点可能更合适。

### 2.3 防止过度建模

AI 必须避免：

- 将所有名词自动转换为节点。
    
- 将所有描述性信息转换为关系。
    
- 为没有实际查询需求的概念创建复杂层级。
    
- 为同一语义设计多个重复标签。
    
- 同时用属性和关系维护相同事实，却缺少同步规则。
    
- 使用大量含义不清的通用关系。
    

设计应该以实际查询需求和数据维护成本为依据，而非以图结构复杂度为目标。

## 三、命名与结构规范

推荐采用以下命名习惯：

|对象|命名规范|示例|
|---|---|---|
|Node Label|PascalCase|`Project`、`TaskExecution`|
|Relationship Type|UPPER_SNAKE_CASE|`DEPENDS_ON`|
|Property|camelCase|`createdAt`、`projectId`|

上述是推荐约定，不是 Neo4j 的强制语法。

标签、关系类型和属性名称大小写敏感，应保持一致。

每种节点类型应优先定义稳定业务 ID。

不要直接将 Neo4j 内部元素标识作为长期业务主键。

## 四、LPG 构建流程

### 4.1 明确业务问题

在设计 Schema 之前，先列出图数据库必须支持的查询场景。

例如：

- 项目包含哪些任务？
    
- 任务之间存在哪些依赖？
    
- 哪个 Agent 负责特定任务？
    
- 某个结论由哪些文档支持？
    
- 一个任务变化会影响哪些其他任务？
    

查询场景是图数据建模的主要依据。

### 4.2 定义初始 Schema

确定：

1. 节点类型
    
2. 每类节点的唯一身份
    
3. 关系类型及方向
    
4. 属性及数据类型
    
5. 数据来源
    
6. 约束与索引
    
7. 典型查询模式
    

AI 不应在未确认业务语义时随意创造节点和关系类型。

### 4.3 数据解析与准备

根据数据源执行相应处理：

- 结构化数据：字段映射、清洗、标准化。
    
- 半结构化数据：解析 JSON、API 响应等。
    
- 非结构化数据：文档解析、分块、实体识别和关系抽取。
    

对于 LLM 自动抽取：

- 明确抽取范围。
    
- 使用 Schema 限制允许的类型。
    
- 区分原文事实和模型推断。
    
- 执行实体消歧与去重。
    
- 保存来源信息。
    
- 校验输出结构。
    
- 对低置信度结果保留待确认状态。
    

### 4.4 数据写入

建议采用：

- 稳定业务 ID
    
- 唯一性约束
    
- 参数化 Cypher
    
- 可重复执行的数据同步逻辑
    
- 必要的事务控制
    

`CREATE` 直接创建数据。

`MERGE` 匹配指定模式，不存在时创建。

注意：MERGE 不能代替实体消歧，也不天然保证任意业务实体的唯一性。

应优先匹配稳定的节点身份，再创建或合并节点间的关系。

### 4.5 数据验证

入库后至少验证：

- 节点类别是否正确。
    
- 节点是否重复。
    
- 关系方向是否符合 Schema。
    
- 是否存在不允许的关系类型。
    
- 属性类型是否正确。
    
- 关键字段是否缺失。
    
- 查询结果是否符合业务预期。
    
- 数据来源是否可以追溯。

## 五、LPG 的核心使用能力

### 5.1 数据管理

使用 Cypher 完成：

- 创建节点和关系
    
- 查询节点和关系
    
- 更新属性与标签
    
- 删除节点和关系
    
- 批量导入与更新
    

### 5.2 图结构查询

包括：

- 节点匹配
    
- 关系匹配
    
- 邻居查询
    
- 多跳遍历
    
- 路径查询
    
- 条件筛选
    
- 聚合统计
    

主要使用 Cypher。

### 5.3 图分析

根据需要使用 Neo4j Graph Data Science：

- 中心性分析
    
- 社区发现
    
- 路径算法
    
- 节点相似度
    
- 链接预测
    
- 图表示学习
    

图算法通常属于额外计算能力，不能将算法输出直接视为确定的业务事实。

### 5.4 图检索

根据检索目标选择：

- 精确属性检索
    
- 范围检索
    
- 全文检索
    
- 向量检索
    
- 图结构检索
    
- 混合检索
    

向量检索需要相应的 Embedding 数据和索引。

### 5.5 GraphRAG

GraphRAG 将图结构、实体关系及文本证据用于增强检索和生成。

推荐流程：

1. 分析用户问题。
    
2. 识别目标实体及查询意图。
    
3. 选择 Cypher、全文、向量或混合检索。
    
4. 按关系扩展相关上下文。
    
5. 获取来源证据。
    
6. 将检索结果交给 LLM。
    
7. 输出具有来源支持的回答。
    

GraphRAG 不等于让 LLM 随意遍历全图。应控制查询范围、检索深度、结果数量和证据质量。

## 六、AI Agent 使用 LPG 的操作规范

### 6.1 查询之前

AI 必须：

1. 获取当前数据库 Schema。
    
2. 确认可用节点标签和关系类型。
    
3. 确认相关属性。
    
4. 确认关系方向。
    
5. 确认数据访问权限。
    
6. 明确查询目标和输出格式。
    

不得臆造数据库中存在的节点或关系。

### 6.2 查询期间

AI 应遵守：

- 优先使用只读操作。
    
- 使用参数化查询。
    
- 根据业务需求限定结果。
    
- 多跳查询设置合理边界。
    
- 复杂查询评估执行计划及成本。
    
- 避免在生产数据库上执行无边界的高成本遍历。
    

### 6.3 写入之前

AI 必须：

1. 确认目标实体的身份。
    
2. 检查是否已经存在相同实体。
    
3. 校验节点标签和关系类型。
    
4. 确保属性符合数据类型要求。
    
5. 确认操作权限。
    
6. 检查是否会造成重复或错误连接。
    
7. 按风险等级执行必要的人工审批。
    

生产环境不应默认开放任意写入 Cypher 的权限。

### 6.4 输出结果

AI 应区分：

- 数据库中明确存在的事实。
    
- 沿现有关系得到的查询结果。
    
- 图算法计算出的分析结果。
    
- LLM 根据证据生成的推断。
    

不能将“存在关联路径”直接解释为“存在因果关系”。

无法获得可靠证据时，应明确说明信息不足。

## 七、知识来源与数据治理

对于知识型 LPG，必须重视可追溯性。

建议根据需要保存：

- sourceId：来源标识
    
- sourceUri：来源位置
    
- createdAt：创建时间
    
- updatedAt：更新时间
    
- validFrom / validTo：事实有效时间
    
- extractionMethod：提取方式
    
- confidence：自动抽取置信度
    
- verificationStatus：审核状态
    

这些字段是建议的应用层规范，不是 Neo4j 自动提供的固定字段。

复杂的事实证据可以采用独立 Claim 节点建模。

例如：

```
(Document)-[:HAS_CHUNK]->(Chunk)

(Chunk)-[:SUPPORTS]->(Claim)

(Claim)-[:ABOUT]->(Entity)
```

当事实之间需要复杂关联、版本控制和审核时，应优先考虑独立事实节点。

## 八、最小可运行示例

### 8.1 创建约束

```
CREATE CONSTRAINT project_id IF NOT EXISTS
FOR (p:Project)
REQUIRE p.id IS UNIQUE;
```

### 8.2 创建节点

```
MERGE (p:Project {id: "p001"})
SET p.name = "示例项目",
    p.status = "active";

MERGE (t:Task {id: "t001"})
SET t.title = "构建LPG",
    t.status = "todo";
```

### 8.3 建立关系

```
MATCH (p:Project {id: "p001"})
MATCH (t:Task {id: "t001"})
MERGE (p)-[:HAS_TASK]->(t);
```

### 8.4 查询关系

```
MATCH (p:Project {id: "p001"})
      -[:HAS_TASK]->(t:Task)
RETURN p.name, t.title, t.status;
```

这组示例展示从 Schema 约束、节点创建到关系查询的基本流程。

对于真实项目，应进一步增加数据导入、权限管理、异常处理和自动化测试。

## 九、设计质量评价标准

评价 LPG 不应以节点或关系数量为主要指标。

应关注以下六个方面：

1. **语义准确性：** 节点和关系是否准确表达真实业务含义。
    
2. **结构合理性：** 标签、属性、关系是否选择恰当。
    
3. **查询有效性：** 能否支持目标查询场景。
    
4. **数据可信度：** 是否可校验、可追溯、可去重。
    
5. **性能与扩展性：** 查询成本是否可控，能否支持后续增长。
    
6. **维护与演进能力：** 是否可以安全扩展和调整 Schema。
    

## 十、AI 设计交付规范

当用户要求设计或修改 LPG 时，AI 应按照以下顺序交付：

1. 业务目标与查询场景
    
2. 关键业务实体及定义
    
3. 节点标签及属性设计
    
4. 关系类型、方向及语义定义
    
5. 完整 Schema 说明
    
6. 样例数据与示例图结构
    
7. Cypher 建图及索引约束
    
8. 数据导入与更新方案
    
9. 核心查询示例
    
10. 数据校验与测试方案
    
11. AI Agent 接入和权限设计
    
12. 已知限制及可扩展方向
    

对于存在歧义的建模决策，AI 应说明选择原因、替代方案及其代价。

**最终原则：**

> LPG 建模的目标，是使用尽可能准确、简洁和可维护的图结构表达业务知识，并支持可靠的数据管理、关系查询与分析。应优先保证语义、数据质量和实际查询价值，而非追求图的复杂程度。
