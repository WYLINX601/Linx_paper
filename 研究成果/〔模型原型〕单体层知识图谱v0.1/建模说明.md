# 单体层知识图谱 v0.1｜讨论与文献案例试表达

这版把传统民居的“分析对象—特征—关系—类型判定—证据”组织成可追溯的图谱。它依据前一轮12篇文献拆解形成，是研究者的建模提案；文献支持建筑学维度，不意味着作者已经提出相同的知识图谱。用户已授权试建，模型尚未逐项确认。

优先阅读：[概念与关系导图](../〔讨论图示〕思维导图/单体层知识图谱v0.1/00-概念与关系.smm.md) → [案例图谱](图谱浏览.html) → [案例与查询检验](案例与查询检验.md)。可继续编辑的[案例导图](../〔讨论图示〕思维导图/单体层知识图谱v0.1/01-文献案例试表达.smm.md)及[独立验收](独立验收.md)位于本轮目录。

## 这版要回答的问题

1. 一个民居研究单元包含什么空间与实体部分，各自的观察范围是什么？
2. 空间如何邻接、通行，构件如何支承；哪些关系尚无证据？
3. 同一对象在什么分类体系、依据哪些特征，被判为哪种类型？
4. 两个来源/案例的同一特征能否比较，差异是否来自口径不同？
5. 任意一条特征或类型判断能否追溯至具体页、图或表行？
6. 能否表达变更与三维关联，以及当前缺少什么资料？

## 三项建模取舍

**空间与物质分开。** 厅堂、院落、天井等属于空间；墙、柱、屋面、构架属于实体部分。墙可以界定天井空间，构架可以跨越多个空间。只在需要独立比较、表达关系或绑定几何时细化为节点，否则保留有对象范围的属性。这避免把文献目录全部机械转换成节点。

**类型与判断分开。** “一字形”或“某原型”是带来源的类型概念；“某对象符合该类型”是一次分类判断。判断保存分类体系、判据、输入特征、结果和归属。原型是作者推辨的参照，匹配原型的形态特征不意味着这座房屋就是最古老原型。

**事实与来源绑定。** 图上的边和特征背后都有断言记录。记录谁作判断、依据哪页材料、描述什么时点、适用哪个局部对象。直接来自论文、读图观察、建模推断、作者成因解释分别标记。没有资料不填写false或0。

## 单体边界及最小采集粒度

Dwelling表示一次单体研究的边界，须说明主屋、附属体、共用院落是否纳入。连片共院、多户合居不凭外观自动合并；无法确定时先保存文献记录。现阶段不要求每根柱、每扇窗都建节点：只有涉及构造/空间关系、局部差异或三维定位的部分才细分。每个对象保留来源内名称与编号。

这版区分“整栋民居”和“侧样/图纸记录”。一个侧样可能只反映某榀构架或剖面，不能把柱筒数当成整栋柱数。不能证实跨篇编号一致时，保存两条记录及待核对应，不自动合并。

## 概念字典

| 概念 | 定义 | 层级 |
|---|---|---|
| 民居研究单元（Dwelling） | 本轮单体分析的对象边界。可含明确归属的主屋、附属体与庭院；不以同姓、同一院落或同一照片自动合并独立住宅。 | core |
| 空间单元（Space） | 可辨识、可命名或具有分析用途的空间范围，如厅堂、房间、廊、天井、院落。空间为空间范围，不等于构件或围护实体。 | core |
| 建筑实体部分（Element） | 可独立指认的体量、构造系统、构架或构件；用elementLevel区分体量/系统/构架/构件，按证据需要细化。 | core |
| 图纸或调查记录（Representation） | 文献中的平面、剖面侧样、照片或表格记录。它是建筑的表述，不是建筑本身；无法确认建筑对应时仍可记录表内特征。 | core |
| 地点或外部空间（Place） | 村落、地块、道路等外部接口，仅保存定位和解释单体所需关系。 | interface |
| 分类体系（TypeScheme） | 带来源、研究区域、分类维度与版本的一套判据；不同文献中的同名类型不默认同义。 | core |
| 类型概念（TypeConcept） | 某一体系内的类别或作者推辨原型；标明普通类别/原型，不把原型视为历史上实存的母体建筑。 | core |
| 变化事件（ChangeEvent） | 有时间或前后状态证据支持的加建、减建、用途改变等事件；类型图的变形操作不能直接生成历史事件。 | extension |
| 三维或二维区域锚点（GeometryRegion） | 绑定模型/图纸的文件版本、坐标系与区域标识；只预留接口，本轮无真实三维数据关联。 | extension |

## 关系字典

所有关系均有方向；对称关系只在明确标记时可对称查询。has_type由分类判断生成，其他关系也须有证据。

| 关系 | 允许的起点 → 终点 | 含义与限制 |
|---|---|---|
| 包含空间（has_space） | Dwelling / Space → Space | 分析边界内的空间包含；同一空间可以跨越多个物理构件。 |
| 包含实体部分（has_element） | Dwelling / Element → Element | 物理组成关系；不能将天井空腔作为木构件。 |
| 围合或界定（bounds） | Element → Space | 某墙面、屋面或构架与空间边界的关系。 |
| 空间邻接（adjacent_to） | Space → Space | 共享或紧邻边界，不能据此推导可通行。 |
| 可直接通行至（direct_access_to） | Space → Space | 有可确认开口/通道的直接通行边；方向有证据时保留，双向需两条断言。 |
| 支承（supports） | Element → Element | 方向从承托构件指向被承托构件；接触不能自动推断支承。 |
| 由图纸或记录表述（represented_by） | Dwelling / Space / Element → Representation | 原文身份对应明确时建立，不以编号相同自动跨文献链接。 |
| 位于（located_in） | Dwelling → Place | 建筑定位到原文明确地点；本轮不补造坐标。 |
| 记录涉及地点（record_about_place） | Representation → Place | 只有记录而缺乏建筑身份时，保留该记录的调查地点。 |
| 被判为类型（has_type） | Dwelling / Space / Element / Representation → TypeConcept | 必须通过带判据/证据的classification记录产生，不能无条件写裸边。 |
| 属于分类体系（in_scheme） | TypeConcept → TypeScheme | 类型概念的命名空间，不表示建筑实体从属。 |
| 是某原型的形态变体（variant_of） | TypeConcept → TypeConcept | 作者阐释或读者建模判断，保留操作规则与归属；不推出真实传播链或年代顺序。 |
| 改变对象（affects） | ChangeEvent → Dwelling / Space / Element | 实际事件对对象的作用，需时间和前后状态证据。 |
| 关联几何区域（anchored_to） | Dwelling / Space / Element → GeometryRegion | 对应对象与模型中的区域；必须有版本、坐标系、区域ID。 |

## 断言与类型判断的最小记录

一条断言记录：对象、关系或特征、值/目标、证据、归属、时点和状态。数值补单位/方法/范围；有争议的多条断言并存，冲突状态明确标记。缺失另记unknown（尚不知）、not_observed（本次未观察）、not_applicable（对该对象不适用），不制造“未知类型”的假实体。

一次类型判断记录：对象、分类体系、类型概念、每条判据、支撑的特征断言、判据满足/不满足/未知，以及整体结果。允许同一对象在平面、构架、屋面等不同维度同时分类；不设一个覆盖全建筑的唯一“总类型”。

这是局部语义模型与可读取数据原型，暂未映射到外部本体标准，也未部署图数据库。后续如需要RDF/Neo4j，先验证定义再转换，避免把软件格式决定当成建筑学结论。

## 本轮可验证与尚待验证

本轮可验证：源内对象识别、特征表达、证据回溯、受限的判据匹配和同维度比较。文献案例的数量及每条结果见案例报告。

尚待验证：单体边界在实地能否稳定划分；跨文献实体去重；房间通行与构件支承关系的完整采集；不同类型方案的可比性；三维区域绑定；同栋跨时间状态。当前文献小样本不能验证全景宁覆盖、民族专属性或方法优于其他方案。

## 后续收敛顺序

先讨论对象边界与最小粒度，再核对这版关系是否回答研究问题；随后选资料完整且身份可确认的住宅补空间/构造关系，记录不能填的项目。只有经过试采修订后，才把相应概念提升为正式字段。共性部分与地域专题保持区分。

## 文件角色

- `模型定义.json`：机器可读的概念/属性/关系及约束定义；本说明解释其建模取舍。
- `案例图谱.json`：本轮文献实例、证据、断言与分类判断；原型事实源。
- `图谱浏览.html`：上述数据的只读可视化投影，重新生成后与数据核对。
- `生成浏览图.py`、`检查图谱.py`：分别从同目录JSON刷新浏览图、复算案例判断及查询报告，保留后续修改后的检查路径。
- 两张 `.smm.md`：可编辑的讨论视图；若修改概念或关系，应同步模型定义并重新验证，避免多个版本无声分叉。
- `案例与查询检验.md`、`验证结果.json`、`独立验收.md`：记录实际检验与适用边界。
